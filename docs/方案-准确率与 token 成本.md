# 准确率与 token 成本：先把账算清，再决定怎么改

- 对象：`api/exam.py`（答案侧）、`api/browser_exam.py`（考场侧）、`api/library.py`（题库）
- 目标：**token 降一半，准确率往上走**。这两件事在这个项目里不矛盾，现在恰好是反着做的。

---

## 一、现在的账

### 每题调用次数

```
solve_current
└─ for _ in range(2):                    ← 最多两轮
     └─ ask_with_check
        ├─ ask_ai()                      第 1 次
        ├─ ask_ai(variant=1)             第 2 次（独立复核）
        └─ 不一致时 ask_ai()             第 3 次（仲裁）
```

- **常态 2 次/题**，不一致时 **3 次**；
- `solve_current` 外面还套了 `for _ in range(2)`，第一轮没匹配出选项就整轮重来 → **最坏 6 次/题**。

### token 估算

单次调用：system ≈ 120 tokens（角色 + 题型说明 + 逐项分析要求 + JSON 格式），user ≈ 170（题干 + 选项），输出 ≈ 40。

| 场景 | 调用次数（85 题） | 估算 token |
|---|---|---|
| 现在的常态 | ≈ 187 | ≈ 6.2 万 |
| 现在的坏情况（部分题 3~6 次） | 250~400 | 8~13 万 |

一门 85 题的卷子，光"复核"就花掉一半预算。

## 二、双答为什么性价比低

这是我要说的核心一句：**双答抓的是抖动，不是错误。**

1. **同源误差高度相关**：同一个模型、同一个 prompt 结构、同一套知识，两次调用错在同一个地方的概率很高。两次说 `A`，很可能是因为**同一个误解**，不是因为 `A` 真的对。
2. **一致性 ≠ 正确性**：`_same_answer` 只是把两个字符串归一化后比对，一致就标 `ai_agree`。它证明的是"模型稳定"，不是"答案正确"。
3. **只有随机错误会被抓**：读题读错、知识点不会、选项映射错——这三类系统性错误，问十次还是错。
4. **还可能白花钱**：答案 `AB` 和 `A、B` 归一化如果不一致，会误判成"分歧" → 触发第三次调用。
5. 现在 `remember()` 很克制，考试答案一律 `status=0`（`browser_exam.py:421-425`），不会污染题库——这点做对了。但代价是**考试答过的题下次也用不上**（`lookup` 默认只返回已确认）。

**结论**：把 2.2 次/题的预算，挪到"异源校验 + 匹配层修复"，是同时省钱和提准的唯一路径。

## 三、准确率到底错在哪

先把错误分类，不然优化就是在猜。六类，按影响面排：

| 类 | 具体表现 | 现在能不能测 |
|---|---|---|
| **D 映射错** | 答案文本是对的，映射到选项时选错（`pick_keys` 双向包含、无归一化、无符号消歧） | 能，已有实测证据 |
| **A 读题错** | 题干被 `clean_title` 切掉关键成分；图片题没走视觉；多小题合并成一句；公式变乱码 | 部分能（有 `_diag_*.py`） |
| **C 知识错** | 模型本身不会 / 记错 | 要金标准 |
| **B 题型错** | 多选当单选、阅读理解当普通题 | 能（对比平台 `typeName`） |
| **E 提交错** | 点了没生效、填了但平台判空 | 能（已回读 input） |
| **F 风控** | 答太快、整卷满分被判异常 | 间接 |

**我的判断：用户感知到的"准确率不行"，很大一部分是 D 和 A**——因为这两类错误会让"明明答对的题"显示成错。而我们现在把预算全花在 C 的复核上（双答），恰好是性价比最低的那一类。

还有一个隐藏风险：`cached_answer()` 里共享题库的答案**直接以 `status=1` 落库**（`browser_exam.py:477-478`）。等于全信共享池。如果别人提交了错答案，我们这边会当成"已确认"永久复用。这条要单独核实共享库有没有交叉验证。

## 四、先建度量（0.5 天，没有它后面都是猜）

### 金标准从哪来

1. **章节测验**：`api/base.py` 已经有完整的成绩回读（`/work/record-detail` 逐题对错 + `mark_wrong`）。这些题和考试题高度重叠，是现成的样本池。
2. **考试批阅后查看试卷**：交卷后平台一般能看成绩；老师若开放答案解析，就能拿到正确答案。
3. 人工在题库页确认过的题。

### 三个必须埋的指标

| 指标 | 怎么看 | 现在的值 |
|---|---|---|
| 题库命中率 | 命中次数 / 总题数 | 未知 |
| **选项匹配失败率** | `pick_keys` 返回空 or 多义的比例 | 未知，我怀疑不低 |
| 二次调用触发率 | 双答不一致次数 / 总题数 | 未知 |

做法：跑一场真实考试，把每题记成一行 jsonl（题干、选项、模型答案、置信、最终选的键、耗时、token），事后跟金标准对。**没有这份数据，任何"提准"都是在赌。**

## 五、五个改动

### ① 单答 + 选项级打分（省最多，也最稳）

现在是"整题给答案"，改成"逐选项打分"：

```json
{"q": 1,
 "items": [{"k":"A","v":0.92,"r":"教材原文"},
           {"k":"B","v":0.05},
           {"k":"C","v":0.71,"r":"符合定义"},
           {"k":"D","v":0.12}],
 "c": 0.88}
```

- **单选**：取 `v` 最大且领先第二名 ≥ 0.25 的；
- **多选**：取所有 `v > 0.5` 的项，再要求"最高分 - 落选最高分 ≥ 0.15"，否则判为不确定；
- `c` 是模型自评的整题置信度，直接当门控信号；
- `r` 一句话理由（≤ 10 字），用于事后审计，不给用户看。

好处：多选不再靠"模型自己数个数"，而是逐项判断，天然支持"少选=0 分"的场景；输出只比现在长 30 tokens，但**只需要 1 次调用**。

### ② 批量（10 题一请求）

system prompt 从 187 次复用变成 9 次。题目之间还能共享课程上下文（同一门课的术语、同一套教材表述），对准确率是正向的。

- 分块 10 题，返回 JSON 数组；
- 解析失败只重发那一块，不重发整卷；
- 主观题单独分批（输出长），一批 3 题。

### ③ 门控：只在"该问第二次"时问

触发二次的条件（满足任一）：

- `c < 0.75`
- 多选且 margin < 0.15
- 选项匹配有冲突（多个候选都过阈值）
- **题库答案与模型答案分歧**（这才是真正的异源信号）

二次调用用**不同策略**，不是复读：换成"先排除错项再选"的提示，或换一个模型。这样两次才有独立性。

按经验这类题占 15~25%，二次预算从 120% 降到 20%。

### ④ 规则层（零 token）

- **判断题**：题干含"不/非/未/无/并非"时，先做一次逻辑取反提示；词表用 `config.ini` 里已有的 `true_list` / `false_list`（`正确,对,√,是` / `错误,错,×,否,不对,不正确`）。
- **绝对化表述**：选项中"一定/必须/所有/都/唯一/完全"这类，在单选题里是强干扰项信号，可写进提示，不额外花钱。
- **"以上都对/以上都不对"**：单独规则处理，模型经常在这里翻车。
- **选项与题干高度重合**：多半是凑数干扰项。

### ⑤ 考后回读正确答案（长期最大杠杆）

这条是我们和 ocsjs 最不一样、也最值得做的地方：

```
交卷 → 打开成绩/查看试卷 → 抓正确答案 → force_answer(evidence="platform")
                                      → mark_wrong(答错的题)
```

- `Library.force_answer()` 已经存在（`library.py:314`），且**不受"已判错不覆盖"的限制**，就是为平台答案准备的；
- 一旦入库就是 `status=1`，下次同一道题**直接命中，0 token**；
- 答错的题同时 `mark_wrong`，防止错答案在题库里循环。

这是唯一能让"越用越准、越用越省"成立的机制。现在考试这条路是断的（考试答案只进 `status=0`，永远不进命中池）。

## 六、预期

| 项 | 现在 | 改后 | 依据 |
|---|---|---|---|
| 调用次数（85 题） | ≈ 187 | 9 批 + ≈ 17 次复核 ≈ 26 次 | 批量 10 + 门控 20% |
| token | ≈ 6.2 万 | ≈ 2.5~3 万 | 估算，需实测 |
| 耗时 | 每题 2~3 次往返 | 9 次批量往返 | 整卷从 20 分钟降到 5~8 分钟 |
| 匹配失败 | 未知 | 显著下降 | 移植 resolver |
| 长期命中率 | 只有共享库/章节测验 | + 考试平台答案 | 回读闭环 |

**准确率我不敢给数字**，因为现在没有基线。但可以给一个可证伪的验收：

> 在金标准样本上对比"单答"与"双答"的准确率。如果差距 < 1 个百分点，就证明双答确实白花钱，直接砍掉。

这个实验本身只要半天，比继续加复核便宜得多。

---

## 七、建议顺序

1. **建度量**（0.5 天）：跑一场真实考试，落 jsonl，和章节测验金标准对齐
2. **砍双答，改单答 + 选项级打分**（1 天）
3. **批量 10 题**（1 天）
4. **匹配层移植**（1 天，上一份文档里的 `api/matcher.py`）
5. **门控 + 异源复核**（1 天）
6. **考后回读正确答案**（2~3 天，单独排期）

前 4 项 3.5 天，能把 token 砍一半，同时把"答案对但选错"这类假错误清掉。

---

## 八、风险

| 风险 | 处理 |
|---|---|
| 批量请求单点失败拖垮整卷 | 10 题一块，失败只重发该块；连续失败降级为逐题 |
| 选项级打分让模型过度谨慎（多选全选） | margin 规则 + 多选"落选项最高分 < 0.15"才补选 |
| 老模型不支持结构化输出 | 保留现有"提取 JSON 子串"的兜底解析 |
| 老师不开放考后答案 | 回读失败就跳过，不影响交卷 |
| 共享题库污染 | 共享答案先落 `status=0`，等平台答案或人工确认再升级 |
