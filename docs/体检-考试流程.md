## 一、结论先说

**后端不卡，开窗也不慢。用户说的「卡在打开页面」，本质是「没有任何进度可看，出错也不说」。**

实测证据：

| 观测项 | 结果 |
|---|---|
| 开窗链路（`POST /api/exam/browser`）首次耗时 | **127 ms** |
| 后端被旁路探针打了 140 次 `/api/status`（开窗期间） | 最大 **701 ms**，绝大多数 < 20 ms |
| 主窗口 UI 线程 `SendMessageTimeout` 探测 151 次 | **全部响应**，0–24 ms，无一 hang |
| 考场窗口实际落地 | 导航到 `mooc1.chaoxing.com/exam-ans/exam/phone/task-exam?...`，标题「考试」，DOM 43 KB，正确渲染出姓名/学号/题量/「开始考试」 |

也就是说：进程没死、服务没堵、页面确实打开了。那用户为什么觉得「打不开」？因为有 5 个地方会让人**停在原地且不知道下一步该干什么**：

1. 已安装的 3.8.8 进「考试」页是**纯空白**——不拉列表、不提示未登录、不给按钮引导；
2. 点「开始」后界面只有一行小字，窗口里如果落在登录页，没有任何说明；
3. 进场判定只认 URL 里的 `enc`，认不到就一直等，**420 秒后**才说一句「等待超时」；
4. 登录是**破坏性**的：打开登录页前先删 `cookies.txt`，登录失败不回滚、不提示；
5. 失败信息是「子进程没有写出结果，请重试」这种，用户拿不到任何动作。

## 三、已确认的问题清单

### P0-1 登录是破坏性操作，失败不回滚

`webui/server.py:850-891`

```python
# 打开登录页之前就删
(ROOT / "cookies.txt").unlink()
(ROOT / "login.json").unlink()
browser_unlock.clear_cookies(win)
win.load_url(LOGIN_URL)
```

- 只要登录页打不开、验证码过不去、或者「我已完成登录」时 `read_cookies` 读不到（`server.py:959-966` 会直接 400），用户就从**「本来能用」变成「什么都没有」**。
- 更糟的是这三步都没有回滚，也没有一句「你原来的登录态还在备份里」。
- **这是「登录不进去」最像的成因**：一次失败的登录尝试会连带把考试列表、刷课全部打回未登录。

### P0-2 同步登录态失败被静默吞掉

`webui/server.py:427-433` + `api/browser_unlock.py:203-247`

```python
try:
    browser_unlock.sync_cookies(win, "考场浏览器", force=True)
except Exception:
    pass
win.load_url(url)
```

`sync_cookies` 拿不到 `CoreWebView2`、或者 cookie 一条都没写进去时**返回 0**，调用方不看返回值，照样导航。结果就是：考场窗口里打开的是**登录页**，而不是考场——用户看到的正是「登录不进去，卡在打开页面」。

### P0-3 进场判定只认 URL 里的 `enc`

`webui/server.py:386-413`（后台线程，每秒一次，开机即跑，永不退出）
`webui/static/app-exam.js:96-127`（前端 1 秒轮询，最多 420 次）

- 判定条件是 `parse_qs(url).get("enc")`。平台换参数名、改用 hash 路由、或者先过一道中间页，这里就**永远命中不了**。
- 超时后只写一句「等待超时，未检测到进入考场」，没有「当前在哪个页面 / 是不是没登录 / 要不要打开独立窗口」任何分支。
- 这个线程对 WebView2 的 `get_current_url()` 是**跨线程调用**，注释里已经承认过 WebView2 只能在 UI 线程访问（`browser_unlock.py:4-7`），这条每秒一次的调用本身就是不稳定源。

### P1-4 已安装的 3.8.8 考试页是空白页

`webui/static/app-base.js` 的 `switchPage()`：

- 3.8.9（源码）里有 `if (!examCourses.length) loadExams();`（第 62-67 行）
- 3.8.8（用户机器上装的）**没有**这段

实测确认：点「考试」→ `#exam-list` 空、无请求、无提示。用户不知道要再点一次「刷新考试列表」。

### P1-5 按钮状态不闭环

`webui/static/app-exam.js:74-93`

```js
btn.disabled = true; btn.textContent = '打开中…';
...
// 成功分支：再也没恢复
```

- 成功后按钮永远停在「打开中…」且 disabled；
- 失败分支只把这一颗按钮复原，其它按钮、提示、列表都不联动。

### P1-6 跨线程阻塞式 `Invoke`

`api/browser_unlock.py:69-92`

```python
form.Invoke(Action(run))   # 阻塞，直到 UI 线程执行完
```

Flask 是 `threaded=True`，请求线程会同步等 WinForms UI 线程；UI 线程忙（正在渲染考场页）时请求跟着等，反过来 UI 线程等 Python 时画面跟着停。这次实测没触发，但**代码路径确定存在**，是「点一下没反应」的结构性来源。同类还有 `exam_embed.py:240-313` 每 0.25 秒一次的 Win32 摆窗循环。

### P1-7 嵌入方案本身高风险

`api/exam_embed.py` 全篇：`SetParent` 把独立窗口改成子窗口 + 每 0.25s 核对位置 + 反复压 `WS_CHILD` 样式。文件注释里已经记录了至少 4 次事故（黑块、跳位、样式被 WinForms 抹掉、attach 失败退化成独立窗口）。

attach 失败的退路是 `make_standalone()`——弹一个**无边框独立窗口**在 (120,90)。用户很可能根本没注意到它，主观感受就是「浏览器页面打不开」。

### P2-8 错误文案不可执行

- 「子进程没有写出结果，请重试」
- 「等了 150 秒还没有结果，请稍后重试」
- 「HTTP 504」

没有一条告诉用户：是没登录、是网络不通、还是平台拒绝了。

### P2-9 子进程用固定临时文件名

`webui/server.py:811`：`chaoxing_exam_list.json`。有进程内锁，但**不跨进程**；两个实例或并发调用会互相覆盖。

### P2-10 日志编码

已安装版的 `chaoxing.log` 是 GBK 落盘。用 UTF-8 打开全是 `鑰冨満娴忚鍣?` 这种乱码——用户把日志贴给我们时基本不可读。

## 四、没能复现的那部分，需要什么才能定位

「有时候」打不开，靠猜没用。开窗链路现在只有一条成功/失败的二元结果，建议加**分阶段打点**（不加也会在改造里自然产生）：

```
open_request(url)
  → cookie_sync(count=24)            # 0 就是 P0-2
  → navigate_start
  → dom_ready(title, url, 关键字)     # 识别「登录页 / 低版本APP / 考试不存在 / 网络错误」
  → gate_detected(类型)               # 验证码 / 人脸 / 平台拒绝
  → enc_detected
```

每次失败把**当前 URL + 页面标题 + 命中的关键字**写进日志。下一次再出问题，一眼就能定位到是哪一段断的。

## 五、和 ocsjs 的对照结论

完整分析见 [方案-闭环改造与 ocsjs 借鉴.md](方案-闭环改造与%20ocsjs%20借鉴.md)。一句话概括差异：

> ocsjs 把「打开页面」这件事**上移给桌面端**（Playwright `page.goto` + 明确超时 + 超时关页），把「必须人来过」的环节做成**阻塞式闸门**（元素在就挂起、元素消失就自动续跑），把状态收敛成 **`start / done / stop / continuate / close` 五个事件**。
>
> 我们恰好相反：开窗逻辑散在 Flask 路由里、进场靠轮询 URL、人工环节靠用户猜。

最值得抄的不是它的答题算法，是这三件工程习惯。
